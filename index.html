Reconstruct

What happened

Describe the event in neutral words, by role and not by person. The review looks for how the system made the event possible, not for someone to blame.

Roles involved

Each role becomes a swimlane. Use roles such as "Night nurse" or "On-call resident", never names. Steps are added in Timeline and drawn in each role's lane in Swimlanes. Open a role to see, edit or add its steps. Click a role's name to rename it.

          Process conditions

          A process condition is something that had to be true for the work to do its job, such as "the responsible nurse receives the result". Record what was required, what was observed, and the evidence. Missing evidence is recorded as not established, which is different from a condition documented as absent.

            Reconstruct

            Shared responsibilities

            List the tasks that more than one role touches. Then ask each role: did you believe this was yours, or another role's? A task nobody believed was theirs is an unclaimed step. Unclaimed steps often sit at the centre of an event and rarely show up in a single person's account. Open a responsibility below to record three further questions separately for each role: could it act, was it expected to act, and would it have to answer for the result. Unanswered questions are shown as incomplete, never as proof that nobody was responsible.

            Analyze

            Causes

            Group contributing factors in a cause and effect diagram. For each factor, keep asking "Why?" and add the answer as a sub-cause, until a cause is specific enough to test a change against. Then write causal statements that link a cause to the event. The review team decides the causes; the tool only suggests factors from the timeline and checks the wording of each statement.

                Analyze

                Risks: failure modes and effects (FMEA)

                Look ahead: where could this process fail next time? Each failure mode belongs to a step, a handoff or a shared responsibility already in this review, so the risks stay tied to the process as it actually works. The team rates each one; the tool only multiplies the team's ratings to rank them.

                Failure modes, sorted by RPN; read severity on its own

                Ratings run from 1 to 10 and are the team's judgement. Occurrence: 10 = very likely to happen. Detection: 10 = very unlikely to be noticed before harm. Severity: 10 = most severe harm. The risk priority number (RPN) is occurrence × detection × severity. It ranks the team's own ratings; it does not decide whether a risk is acceptable.

                Driver diagram

                The team's theory of change: the aim, the primary drivers that most directly affect it, the secondary drivers that feed them, and the change ideas to test. Change ideas are the actions recorded in Actions. Each driver records which findings from this review it came from, so every proposed change can be traced back to what the review found.

                  Improve

                  Actions

                  Each causal statement should lead to at least one action. Actions that change the system, such as forcing functions or simpler processes, tend to hold up better than actions that rely on people remembering, such as training or a new policy. Link each action to the drivers it is meant to move and the failure modes it should reduce, then give it a measure and the point when its test starts. Measure shows whether it made a difference.

                    Improve

                    Did the actions work?

                    Each action is a test of change. Choose a measure to see its run chart. The point where each linked action's test started is marked on the chart, so you can see whether the change made a difference. With 10 or more points the chart draws the median.

                    Actions tested on this measure

                    Shift and trend signals use common run chart rules: six or more points in a row on one side of the median is a shift; five or more points in a row going the same direction is a trend. These rules are not part of the IHI run chart instructions this tool follows, and are signals to discuss, not proof.

                    About this tool

                    This is an early prototype built on the ICA Project Cloud model: each role is a workstream with its own lane, a shared responsibility is a constraint several workstreams touch, and handoffs are exchanges across lane boundaries. A review shows where independently organized work met and failed to connect.

                    The methods follow quality improvement tools described by the Institute for Healthcare Improvement (cause and effect diagram, flowchart and run chart, from the QI Essentials Toolkit) and the RCA² approach to root cause analysis, including its rules for causal statements and its action hierarchy. All wording here is original. This tool is not affiliated with or endorsed by IHI. The original materials are at ihi.org.

                    The six process domains used for process conditions (demand and capacity, information integrity, responsibility and decision rights, handoff and dependency continuity, execution and functional completion, adaptation and interruption capacity) are provisional analysis categories for this tool. They are not a validated implementation of ICA theory.

                    The tool records what people tell it. It does not decide root causes, rate anyone's performance, or determine fault. An absent record is reported as "not established", never as proof that something failed.
